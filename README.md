# SAP Development Specification Builder

> Turn SAP business requirements into functional specifications checked against the SAP system, and into structured GitHub Copilot development specifications.

A small, static web app with two modes (toggle **Functional | Technical** in the header):

- **Functional** – functional consultants and business analysts write a functional specification (FS) for **SAP or any other system**, or before the system is decided. A business requirement is enough to start; AI can draft the rest for review. SAP specs can be checked against the live DEWA SAP system through a read-only Copilot agent. Download as **Word** or Markdown. See [Functional specifications](#functional-specifications).
- **Technical** – an SAP developer gives GitHub Copilot the right context **before** coding starts. Fill in a requirement in 5–10 minutes, download `BUSINESS_REQUIREMENTS.md` (or send it straight to VS Code), and hand it to Copilot (VS Code or Eclipse ADT).

- **No backend, no database, no login, no AI API.** Open `index.html` — that's it.
- **Private by design.** Requirements never leave your browser. Drafts are kept in the browser's local storage only.
- **Easy to share.** Send the `.md` or a share link. Or host the folder on any static host.
- "AI studio" look in the MoroHub colours (lime on charcoal): light by default with a dark theme (☾ in the header), glass panels, animated aurora, a readiness ring, a streaming reveal + confetti when the spec is generated (all motion is switched off when the OS asks for reduced motion).
- Keyboard first: **Ctrl/⌘ K** command palette (steps, examples, add objects, download, share, theme…), **Alt + ← / →** between steps, **Enter** for the next grid row.

## How to run

```text
open index.html          # double-click it; works from file://
```

Optional: serve the folder with any static host (GitHub Pages: *Settings → Pages → Deploy from branch → root*).

## Functional specifications

```text
Requirement → (✦ Copilot generates the spec | reads an existing program) → Process & requirements → Solution & sign-off
            → Word / Markdown → RICEFW item or program → Development spec (Technical mode) → dewa-abap
```

Only the business requirement is needed. Everything else can be generated by Copilot, read from an existing program, or
filled in by hand – rarely used fields sit under **More details** in each step.

### SAP or any other system

Step 1 starts with **Where will this run?**

| Choice | What changes |
|---|---|
| **SAP** | Everything below: module (mandatory), org units, transactions and Fiori apps, *Read an existing program*, RICEFW, SAP discovery, hand-off to a Technical spec. |
| **Other system** | Optional system name (e.g. "Salesforce", "in-house portal"). SAP-only fields are hidden and the wording is generic: *System / screen* instead of transaction, fit-gap *standard feature / configuration / new development*, roles & access, interfaces, outputs. The document shows **System** instead of Module and has no SAP sections. |
| **Not decided yet** | Like *Other system*; the document says *System: To be decided*. Only the business need is asked. |

Only the **business requirement** is mandatory for a non-SAP spec. Drafts from before this choice open as SAP specs.

### Three steps

| Step | Shown | Under *More details* |
|---|---|---|
| 1. Requirement | System choice, title, **business requirement** (and **module** for SAP), **✦ Generate the whole spec with Copilot**, **Read an existing program** (SAP), *Create document now* | Process area, objectives, KPIs, scope, stakeholders, org units, module templates |
| 2. Process & requirements | TO-BE steps (step, role, transaction / app with type-ahead by description, change) and the flow; FR-01 … with MoSCoW priority, **fit-gap**, acceptance criteria; business rules | AS-IS steps ("Start TO-BE from AS-IS"), current program logic and objects read, variants, data requirements |
| 3. Solution & sign-off | SAP: **current SAP system** (discovery, below), RICEFW items (R-01, E-01 … per type) and the hand-off to a **Development Specification**; other systems: roles, interfaces, outputs. Then UAT scenarios (*Create UAT skeleton from FRs*), approvers, "Ready for sign-off" check → **Generate** | NFRs, risks, document control (ID, version, status, author, history); SAP roles, interfaces, outputs, SPRO notes |

### Generate the whole spec with Copilot

- **✦ Generate the whole spec with Copilot** (step 1) writes title, objectives, KPIs, scope, stakeholders, AS-IS / TO-BE steps, functional requirements with acceptance criteria (and fit-gap for SAP), business rules, data, roles, interfaces, outputs, NFRs, test scenarios and risks from the requirement.
  - **In VS Code:** *Generate with Copilot* (background, no tools, no system access) or *Generate in Copilot Chat* (watch and steer it; Chat sends the result back with `dewa_submitFsDraft`).
  - **In the browser:** *Copy AI prompt*, paste it into an AI chat your organisation allows, and paste the answer back. The builder itself never sends anything.
  - A **review dialog** shows what would be added per section; pick what to keep. Only empty fields are filled and new rows are appended – nothing typed by hand is changed. Assumptions are marked `[TO BE CONFIRMED]`. The document opens right after; *Review Details* goes back to the steps.
- **Create document now** creates the document from what is there; everything missing is listed under *Open questions*.

### Read an existing program (SAP)

Name programs, transactions, classes or function modules (e.g. `ZFI_AGEING, FBL1N`) in step 1. Copilot reads them, the
objects they use and the SAP system **read-only** through the SAP MCP servers (same tool filter as discovery: read
tools only, write verbs always excluded) and describes the current logic in business words.

- **In VS Code:** *Read automatically* (progress log in the panel) or *Read in Copilot Chat* (`dewa-fs-discovery`, which hands the result back with `dewa_submitFsDraft`).
- **In the browser:** *Copy prompt* → Copilot Chat in VS Code with `dewa-fs-discovery` → paste the answer under *Paste the AI answer*.
- After the review, step 2 shows the **current program logic**, the objects read, AS-IS steps, business rules, data and the current behaviour as FRs. The document gets a **Current System** section.
- **→ Technical spec: change …** (step 3 and the finished document) creates a Development Specification with the program as the object to change and the objects it uses as existing objects, for `dewa-abap`.

**Output** – `FS_<Module or system>_<Title>.docx` (title page with document control, contents, numbered headings, tables, header with document ID and version, *Page X of Y* footer) and `FUNCTIONAL_SPECIFICATION.md`, both from the same content, in at most eight sections:

1. Business Requirement & Scope (objectives, KPIs, scope, stakeholders)
2. Process (current, proposed with flow, variants)
3. Functional Requirements (FRs with acceptance criteria, business rules, data)
4. Current System (current program logic; SAP system context from discovery)
5. Solution (fit-gap & traceability FR → solution → RICEFW → UAT, RICEFW items, roles, interfaces, outputs)
6. Testing & Quality (UAT scenarios, NFRs)
7. Risks & Open Questions
8. Document Control (version history, approvals)

Unknown values read `[TO BE CONFIRMED]`; empty sections are left out. Transactions and Fiori apps are entered in the process
steps (type-ahead by description, including what discovery found), not in a separate section.

### System discovery (read-only, through Copilot)

The browser never connects to SAP. DEWA's VS Code already has GitHub Copilot with the **SAP ABAP ADT, Fiori, UI5 and CAP MCP servers**; the read-only agent [`dewa-fs-discovery`](vscode-extension-addon/agents/dewa-fs-discovery.agent.md) uses them to read what exists and returns a JSON **context pack** (`dewa-sap-context-pack`, v1: system/release, objects, transactions, Fiori/UI5 apps, CAP services, BAdIs, customizing hints, not-found list).

1. Step 3 → **Discover in SAP**: the builder copies a prompt built from the FS (module, scope, FRs, every transaction/table/object named, proposed new names) and opens VS Code.
2. With the DEWA extension add-on, Copilot Chat opens with `dewa-fs-discovery` and the prompt filled in. Sign in to Copilot if VS Code asks (VS Code's own sign-in), review, press **Enter**.
3. Copy the agent's answer → **Import from clipboard** (or paste it). The pack is validated and treated as untrusted data.

The FS then shows a *Current SAP System Context* section, a **reference check** (✓ in system · ✗ not found · ⚠ proposed name already exists · – not checked), discovered names as suggestions in the grids, and a warning when the pack is older than 30 days. *Try a sample pack* shows the flow without a system ([`docs/samples/fs-context-pack-sample.json`](docs/samples/fs-context-pack-sample.json), clearly marked as sample).

### Inside VS Code (one window)

**Install:** [`dist/dewa-sap-spec-builder-1.0.7.vsix`](dist/dewa-sap-spec-builder-1.0.7.vsix) → VS Code → Extensions → `…` → *Install from VSIX…* (or `code --install-extension dewa-sap-spec-builder-1.0.7.vsix`). It installs next to DEWA's existing extension and adds the `dewa-fs-discovery` agent to your prompts folder. Rebuild it with `node scripts/build-vsix.js` (source: `vscode-extension/` + `vscode-extension-addon/`).

**DEWA: Open SAP Spec Builder** (command palette or *Spec Builder* in the status bar) opens this same app as a tab inside VS Code:

- **Read an existing program** (step 1, SAP) reads it read-only with the Copilot model and the read tools of the SAP MCP servers, or in Copilot Chat with `dewa-fs-discovery`; the logic comes back for review;
- sign in to **GitHub Copilot** in VS Code (button in step 1 or 3 or the Accounts menu);
- **Discover automatically** reads the system read-only with the Copilot model and only the *read* tools of the SAP MCP servers (write tools are filtered out), with live progress and automatic import — or **Run in Copilot Chat** beside the panel, where the agent sends the pack back with the `dewa_submitContextPack` tool;
- **Generate with Copilot** (step 1) writes the whole spec in the background; **Generate in Copilot Chat** runs it visibly in Chat, where you can steer it – Chat sends the result back with the `dewa_submitFsDraft` tool and the builder opens its review dialog;
- **Open in Copilot Chat** on a functional spec (preview or finished document) asks Copilot to review it – gaps, contradictions, untestable requirements, open questions – and then answer your questions; in Technical mode it hands the spec to `dewa-abap`;
- Chat **sends the prompt automatically** (setting `dewaSpecBuilder.chatAutoSend`, default on; off = the prompt is only filled in and you press Enter);
- Word / Markdown are saved through VS Code's save dialog.

**VS Code extension add-on** – [`vscode-extension-addon/`](vscode-extension-addon/INSTALL.md): the panel, the automatic discovery runner, the submit tool, the `/builder` and `/discover` URI handlers, the agent file, install steps and unit tests (`node --test vscode-extension-addon/test/*.test.js`). In the browser without the add-on, choose *Plain VS Code (copy & paste)* in step 3 → *VS Code launch settings*.

## How developers use it (Technical mode)

```text
Business Requirement → Select Object → Add Existing/New Objects → Add Important Rules
        → Review → Generate .md → GitHub Copilot → Development
```

| Step | What you do |
|---|---|
| 1. Build | Pick Report / ABAP Class / RFC / RAP / CDS / CAPM / DDIC / Enhancement / OData / Fiori / Form and paste the business requirement (the only two mandatory inputs). The main object is added automatically. |
| 2. Requirement | Optional objective, users, expected output, business rules, acceptance criteria, assumptions. |
| 3. Objects | One compact line per object: type, name, status (**Existing – reuse**, **Existing – change**, **New**, **To Be Confirmed**), purpose. Suggestions are offered, never assumed. A dependency map is drawn from the list. |
| 4. Specify | A designer per new / changed object (see below). For reused objects: "what do you need from it?". Plus authorization (authority-check grid), testing, clean core. |
| 5. Review | "Ready for Copilot" check, counts, open questions, editable Definition of Done → **Generate Specification**. |

### Object designers (step 4)

| Object | What you specify |
|---|---|
| Table (SE11) | Delivery class, client dependency, maintenance, **fields grid** (field, key, data element, type, length, decimals, domain, description, currency/quantity reference, check table), includes, TMG; advanced: data class, size category, buffering, enhancement category, indexes, logging |
| Structure / Data Element / Domain / Table Type | Components, field labels (10/20/40/55), built-in type & length, fixed values, value table, conversion routine, line type, access mode, keys |
| Search Help, Lock Object, Message Class, Authorization Object | Parameters, lock mode & parameters, messages (No./type/text), authorization fields & values |
| Report (SE38) | Selection screen grid (SELECT-OPTIONS / PARAMETERS, FOR/TYPE, selection text, obligatory, default), processing logic, output type, ALV column grid, background job, file layout |
| Class / Interface (SE24) | Superclass, interfaces, FINAL/ABSTRACT/CREATE…; **any number of methods** (add 1 or "how many?"), each with visibility, static/instance, kind, signature grid (IMPORTING/EXPORTING/CHANGING/RETURNING, typing, type, optional, default, VALUE( )), exceptions, logic, unit tests; attributes / constants |
| Function Module / RFC (SE37) | Function group, processing type, **Import / Export / Changing / Tables parameters**, exceptions (classic / class-based), BAPIRET2 RETURN, COMMIT handling, logic, error handling; RFC: destination, sRFC/aRFC/tRFC/qRFC/bgRFC, S_RFC |
| CDS (ADT) | Entity type, VDM layer, data source, parameters, joins, associations/compositions with cardinality, element list (key, alias, annotations), WHERE, access control (DCL) |
| RAP | Implementation type, strict / draft, behavior pool, **entities** (root/child, tables, draft table, operations, lock/authorization/etag master, field control, determinations, validations, actions), projection, service definition & binding, UI annotations |
| CAPM | Runtime, database, **entities with elements**, services with exposed entities / actions / events, custom handlers, external services, auth (XSUAA/IAS), roles, UI, deployment (MTA / Kyma) |
| OData, API, Fiori/UI5, BAdI / Enhancement, Form, Background Job, Workflow | Entity sets & functions, payload & errors, app type & pages, enhancement spot / exit & logic, form interface, job schedule, workflow steps |

Grids accept **Paste from Excel** (tab-separated, same column order) and **Enter** moves to the next row (adding one at the end). Customer DDIC objects referenced in grids but not listed (e.g. a Z data element in a table field) are offered as one-click "+ add" chips.

A live Markdown preview sits next to the form (an Edit/Preview tab on small screens).

### RAP: readiness checks and implementation blueprint

RAP builds fail most often on structure that the agent has to guess. The builder now derives that structure from the RAP designer and the Table / CDS objects:
- **Readiness checks (step 4, RAP card)** flag what would break activation:
  - an ETag field that is not a CDS element;
  - a missing total ETag for draft;
  - missing admin fields (created / changed by and at);
  - a missing lock or authorization master;
  - an unnamed draft table.

  One-click fixes add the admin fields to the table and CDS, and add the draft table.
- **RAP Implementation Blueprint** in `BUSINESS_REQUIREMENTS.md`:
  - artifacts and **activation groups** (Dictionary → Data model → Behavior → Service);
  - the behavior definition skeleton for the interface and the projection (draft actions, ETags, mapping);
  - the **behavior pool skeleton** (`ABSTRACT FINAL FOR BEHAVIOR OF`, a handler class with every method signature);
  - the admin-field table and the draft-table rule.
- **Copilot instructions:**
  - build from the blueprint;
  - activate group by group, without asking the user for each object;
  - stop after 3 failed activation rounds and report.

For the agent side, [`docs/agent-kit/dewa-abap-RAP-update.md`](docs/agent-kit/dewa-abap-RAP-update.md) is a drop-in "RAP build mode" section for `dewa-abap.agent.md`. The same content is also a skill: [`docs/agent-kit/skills/rap-build/SKILL.md`](docs/agent-kit/skills/rap-build/SKILL.md).

## Essential vs. advanced fields

Each object shows its essential questions first; optional ones (e.g. table technical settings, class attributes, RAP mapping and side effects, CAP multitenancy) sit behind *Advanced details ▸* on that object. Performance questions appear only for development types where they matter (Report, RFC, RAP, CDS, CAPM, OData).

## Generated Markdown

`BUSINESS_REQUIREMENTS.md` with only the relevant sections, numbered automatically:
Requirement · Development Object · Business Objective · Existing / New Objects · Dependencies · Functional Requirements · Technical Details · Business Rules · Input · Output · Authorization · Error Handling · Performance · Testing · Acceptance Criteria (Given/When/Then) · Clean Core · Assumptions · Open Questions · Definition of Done · Copilot Development Instructions.

Rules baked in: nothing is invented, unknown values become `[TO BE CONFIRMED]`, no empty sections, and tables/lists are preferred to prose to keep tokens low.

## Sharing

| Option | What it is |
|---|---|
| **Open in VS Code** | One click copies a ready prompt (one-line instruction + the full specification) to the clipboard and launches VS Code. In VS Code press **Ctrl+Alt+I** (Copilot Chat), **Ctrl+V**, **Enter**. The browser asks once for permission to open VS Code; it cannot type into VS Code itself. |
| **Download file** / **Copy Markdown** | `BUSINESS_REQUIREMENTS.md` – the specification for Copilot. |
| **Upload** (header) | Opens a downloaded `FUNCTIONAL_SPECIFICATION.md` or `BUSINESS_REQUIREMENTS.md` again as a new draft, in the right mode. Downloaded files end with one hidden comment (`<!-- spec-builder-state:v1 … -->`, invisible in Markdown previews) that holds the builder data, so the spec comes back exactly. Edits made in the `.md` itself are not taken over (the builder says so). Older files without that comment are read best-effort (requirement, scope, steps, FRs and rules; objects and rules for a development spec). |
| **Copy share link** (🔗 in the header) | The project is encoded in the URL fragment (`#s=…`). Whoever opens it gets a copy as a new local draft. The fragment is not sent to any server, but anyone you send the link to can read the requirement, so treat it like the file itself. |

The model in `state.js` does not depend on Copilot; Copilot is just an **output profile** in `markdown-generator.js`. Claude Code, Codex, Cursor and others can be added as further profiles.

## Adding or changing object types

1. Edit `config/object-definitions.json`:
   - `devTypes` – the step-1 cards (`label`, `hint`, `mainObject`, `performance`).
   - `objectTypes` – one entry per object with `group`, `tcode`, `usedHint` and `fields`. A field has `id`, `label`, `kind` (`text | textarea | lines | select | radio | multicheck | check | grid | records`), optional `advanced`, `showIf`, `ask` (open question when empty), `placeholder`. A `grid` has `columns` (`id`, `label`, `kind`, `w`, `ref` for "unlisted object" detection, `list` for type suggestions); `records` has `itemLabel`, `titleField` and nested `fields`.
2. Run `node scripts/build-config.js` to regenerate `js/config-bundle.js` (`--check` verifies it is current).
3. Reload. No UI code changes are needed; `section` decides where the value lands in the Markdown.
